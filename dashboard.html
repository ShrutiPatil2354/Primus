SECTION 1

Big picture — what is actually happening

PRIMUS is one Python process serving a web dashboard. Every message runs the same pipeline: perceive → classify intent → retrieve from memory → answer or act → store what happened → speak. Nothing is answered from pretrained world knowledge — the LLM is constrained to use only what the local memory cortex contains.

The agent loop

app.py builds the Gradio UI and binds every input (send button, Enter, mic stop, doc upload) to one function: handlers.process_input() — 9 inputs → 17 outputs, so chat, voice player, task plan, action log, and dashboards can never drift apart. A gr.Timer(1.5 s) re-renders live panels continuously.

WHY — one pipeline + one refresh loop = no divergent UI states. Heavy libraries (whisper, piper, torch, cv2) are imported lazily inside functions so startup stays fast.

The zero-prior guarantee

Task and fact questions are answered only from learned memory; unknown tasks are refused ("Teach me first"). The Knowledge Gate runs before the LLM, and the LLM gets a strict tabula-rasa system prompt so it may only rephrase taught knowledge. Wipe data/primus_memory.db → a true blank slate.

WHY — this is the project's core claim: local, auditable knowledge instead of hidden pretrained guesses. Demos: "How to make tea?" → refused; teach it; ask again → answered from your steps only.

The layers (dependency rule)

app.py → ui/handlers → core + perception + metrics. Dependencies point one way only — nothing in core/, perception/, or metrics/ imports from ui/. src/training/ runs offline as its own process; cpp_core/ is a compiled primus_core.pyd imported with a pure-Python fallback.

WHY — one-way dependencies keep the brain testable without a UI, and the UI swappable without touching cognition.

SECTION 5

Memory management — the five cortices

src/core/memory.py is the agent-facing API; src/core/storage.py is the durable store behind it (one STORE singleton, RLock-guarded, SQLite → Postgres). The split mirrors the brain: fast, structured access on top; durable, bounded storage underneath.

Procedural

How-to knowledge. Skills: id, name, steps[], confidence, perception, timestamps. Born at confidence 0.5; every edit appends an immutable skill_versions row (v1, v2…). Retrieval = name-token match.

Episodic

The diary. Timestamped events: taught, recall, perform, rejected, edit, delete, clarification, conversation, example. Newest-first; shown 30 in the UI, kept 2 000 in the DB.

Semantic

Facts about the world/teacher. Regex extraction of “my name is…”, “I like/love/prefer…”, “remember that…” into key→value rows (user_name, user_prefers, fact). Same key overwrites.

Sensory

The last things seen/heard. Camera summaries and audio transcripts (120-char slices). Rolling window: 20 shown, 200 kept. Gives the LLM ambient context without video frames.

Working

Current consciousness. Key-value scratchpad rewritten every turn: last_intent, last_skill, last_perception, updated timestamp. Exactly what “I am thinking about right now” means.

How a write flows (example: teaching)

  • handlers parses “Learn X: a; b; c” → memory.add_skill(name, steps)
  • _lock acquired → load snapshot → upsert skill (keeps existing confidence) → version row appended
  • STORE.record_feedback(sid, "learned", 0.5, …) — the reward log starts here
  • memory.add_episode("teach", …) — the diary entry, trimmed to 200
  • UI tables refresh via the 17-tuple and the 1.5 s timer
WHY SNAPSHOTS? — snapshot()/replace_snapshot() mirror the legacy memory_bank.json shape, so old code (and the one-time JSON→SQLite migration) keeps working while new tables evolve underneath.

Multi-agent isolation

Custom agents get private cortex tables: agents, agent_skills, agent_documents, agent_feedback keyed by (agent_id, id). The Default Memory remains shared. A document taught to one agent is invisible to others — enforced at retrieval, not by prompt.

  • Teach/ask/feedback paths pick the table set by whether an agent is active
  • Deleting an agent cascades: skills → documents → feedback
  • Reset (“clear learning data”) truncates cortex tables but keeps schema & settings
WHY ISOLATION? — a tutor bot and a cooking bot must never leak knowledge into each other; DB-level partitioning is stronger than any prompt instruction.

SECTION 6

Retrieval — how the right memory is found

Retrieval always runs before the LLM and decides whether the LLM even gets a chance. Three stages, in order: route the intent → match a procedure → score the documents. A vector path (pgvector) is pre-wired for later.

Stage 1 · Intent routing

Ordered keyword tables in intent.py: self-keys → teach-keys → task-query-keys → perform-keys → fallback conversation. The message is split on !? \n; mixed intents become multiple (asks you to send one at a time). Composer mode can force teach (Learn) or demote it (Ask).

WHY KEYWORDS, NOT AN LLM? — routing must be instant, deterministic and free; an LLM router would add latency and could misroute the very gate that guarantees zero-prior.

Stage 2 · Procedural match — find_skill()

① tokenize the query (\w+, lowercased) → ② subtract the stopword set (“how, to, make, cook…” — request words that can’t identify a task) → ③ for each skill, intersect with name-only tokens → ④ score = |overlap|, +3 if the skill id appears verbatim → ⑤ best score wins, else None.

WHY NAME-ONLY + STOPWORDS? — matching step words once returned the wrong recipe because two tasks share verbs like “add” or “pour”. Stopwords stop “how to make tea” matching “coffee”; name-only matching stops step-word collisions. Deterministic and auditable beats clever.

Stage 3 · Document scoring

For the active agent: query tokens (len>2) are counted in each stored document’s name+content; best count wins. An excerpt is built around the hits and sent as the only allowed source to the LLM (temperature 0.0, system rule: “if the excerpt lacks the answer, reply with the fallback phrase — do not guess”).

WHY EXCERPTS? — keeps the prompt inside the 4096-token window and makes the answer verifiable against a stored slice instead of the whole file.

Vector retrieval — pre-wired, not yet driving

The Postgres backend already creates semantic_documents(content, embedding vector(384)) with upsert_embedding() and cosine nearest-neighbour search (1 − embedding <=> query). SQLite has no vector index, so today keyword scoring drives retrieval; the STORE interface is identical, so embeddings can be switched on without touching handlers.

WHY WAIT? — the corpus is small and teacher-curated; exact matching is more predictable than embeddings, costs no VRAM and works offline. The pgvector column is the migration path once knowledge grows.

What the LLM actually receives (conversation path)

  • System prompt: strict tabula-rasa rules — never answer medical/factual/how-to questions from pretraining; must reply with a taught fallback phrase otherwise; may freely discuss its own state.
  • Injected knowledge: memory.summary() / STORE.agent_summary() — every skill as [SKILL id] step → step, every fact as [FACT] key: value, agent domain + rules, plus document previews (1 000 chars each).
  • History: the last 12 chat messages; perception: current camera labels when enabled.
WHY THIS SHAPE? — the model is treated as a language renderer for stored knowledge, not a knowledge source. Refusals are therefore reliable: if the memory summary doesn’t contain it, the prompt forbids inventing it.
SECTION 7

Learning & RL — two timescales, one data source

Every teach/recall/perform/unknown event writes a reward into feedback_events. Two learners consume that stream: an instant confidence rule (in C++) and an offline meta-RL trainer.

① Synaptic confidence — online

new = old + 0.15 · (reward − old), clamped to [0,1] — an exponential moving average toward observed reward. Runs inside primus_core.pyd (C++17/pybind11); engine.py falls back to the byte-identical Python formula if the build is absent.

  • learned / taught → reward 0.5 (neutral start)
  • recall, perform, execution → 1.0
  • unknown / rejected → 0.0
WHY EMA? — one float per skill, smooth, bounded, interpretable in the UI; no gradients in the request path.

② Meta-RL policy — offline

python -m src.training.meta_rl trains a 32→64→5 MLP (teach/recall/perform/revise/unknown) over stored feedback. Context = 32-dim hashed bag-of-words of skill name + steps. Per-task adaptation on half the episodes, evaluated on the held-out half; meta-update pulls base weights 10% toward the adapted ones. Checkpoint: data/knowledge_meta_policy.pt (--resume supported).

WHY REFUSE TO TRAIN EARLY? — it requires ≥2 tasks × ≥2 episodes for a held-out split; without that gate it would memorize noise and quietly break the zero-prior story.

③ Robot-episode data path

The safe tabletop sandbox records robot_episodes(task, actions_json, reward, success); evaluation.export_jsonl() dumps them to data/robot_training.jsonl for offline evaluation or future policy training. Robot trajectories are deliberately excluded from the knowledge meta-RL domain (task_knowledge).

WHY SIMULATION ONLY? — it creates state-action-reward data with zero hardware risk; real actuators are a later phase.
WHY TWO TIMESCALES? — the confidence rule gives immediate, visible adaptation per event; meta-RL needs batches and runs as its own process on the same feedback log. One recorded stream feeds both, so nothing is labeled twice and the dashboard never blocks on training.
