1. Executive summary

PRIMUS is a Gradio-based, local-first AI agent studio. A user selects or creates an isolated agent, teaches procedures or uploads knowledge, and then asks questions in Ask Mode. The application routes each input through speech/document/perception handling, intent classification, the knowledge gate, retrieval, optional Ollama generation, memory persistence, voice output, and dashboard refresh.

Core promise: a custom agent should answer from its explicitly taught procedures and uploaded documents. If the required knowledge is absent, the agent returns an unknown-knowledge response instead of inventing an answer.

2. System context

flowchart LR U[User] --> UI[Gradio web UI] UI --> H[src/ui/handlers.py] H --> I[Intent router] H --> K[Agent knowledge gate] H --> M[MemoryStore] H --> L[Ollama / LLM] H --> P[Perception] H --> X[Executor] H --> O[Dashboard outputs] P --> A[Speech recognition] P --> V[Camera / vision] O --> UI M --> DB[(SQLite primus_memory.db)] L --> H

The dependency direction is intentionally one-way: app.py → ui/handlers.py → core, perception, metrics. Core and perception modules do not import the UI layer. This keeps the business flow testable and prevents UI code from becoming a dependency of storage or cognition.

4. Application startup and live refresh

The timer is not the source of truth; it re-reads the source of truth. Chat and learning handlers persist changes first, and the next gr.Timer tick redraws the dashboard. This keeps Activity, Memory, and Task Library synchronized after a request.

6. Knowledge and data model

erDiagram agents ||--o{ agent_skills : owns agents ||--o{ agent_documents : owns agents ||--o{ agent_feedback : produces skills ||--o{ feedback_events : receives skills ||--o{ skill_versions : has agents { text id PK text name text domain text instructions text created text updated } agent_skills { text id PK text agent_id FK text name text steps_json real confidence text updated } agent_documents { text id PK text agent_id FK text name text content text created } agent_feedback { integer id PK text agent_id FK text skill_id text event real reward text detail }

Uploaded files are decoded by _read_document_text(). Supported text-like files are read directly; PDFs use pypdf when available. The file is stored as document content under the selected agent. Retrieval uses token overlap in find_agent_document(), followed by a bounded excerpt. The LLM receives only that excerpt and a strict instruction not to use outside facts.

7. Document upload flow

flowchart TD A[User selects file] --> B{Selected custom agent?} B -- No --> C[Show validation warning] B -- Yes --> D[_read_document_text] D --> E{Text extracted?} E -- No --> F[Show extraction warning] E -- Yes --> G[Store agent_documents row] G --> H[Store learnt feedback value 0.75] H --> I[Return friendly confirmation] I --> J[Timer refreshes Activity, Memory, Task Library]

Document learning is recorded as learnt = 0.75. Explicitly taught procedures are recorded as learnt = 0.5. A successful answer from a skill or document is recall = 1; an unavailable answer is unknown = 0.

8. Ask Mode: question-to-answer flow

sequenceDiagram participant User participant UI participant P as process_input() participant Gate as Knowledge gate participant Store participant LLM User->>UI: Type question / send voice / attach file UI->>P: text, audio, history, agent_id, mode, document P->>P: Transcribe audio if present P->>P: Add camera context if enabled P->>Store: Ingest document if attached P->>Gate: Classify intent and enforce Ask Mode Gate->>Store: Search agent skill alt Known procedure Store-->>P: Skill and ordered steps P->>Store: Save recall=1 else Matching document Store-->>P: Document excerpt P->>LLM: Strict prompt + excerpt only LLM-->>P: Answer or fallback P->>Store: Save recall=1 else No matching knowledge P->>Store: Save unknown=0 P-->>UI: Unknown-knowledge response end P-->>UI: Chat, activity, memory, plan, voice, task outputs

Example using the legal document

  1. Upload legal_contract_review_policy.txt to Legal Advisor.
  2. Ask: “What should I check for termination and renewal?”
  3. The token search finds the legal checklist and returns an excerpt-based answer.
  4. Activity records recall with value 1.
  5. Ask: “What is the enforceability of this contract under local law?”
  6. That jurisdiction-specific answer is outside the document, so the agent refuses and records unknown with value 0.

9. Learn Mode: teaching-only flow

flowchart TD A[User switches to Learn Mode] --> B{Input type} B -- Explicit task --> C[Parse task name and steps] C --> D[Store agent_skills] D --> E[Store learnt=0.5] E --> F[Update task library and learning activity] B -- Document upload --> G[Store agent_documents] G --> H[Store learnt=0.75] H --> F B -- Question or casual text --> I[Do not answer or learn] I --> J[Ask user to switch to Ask Mode]

Explicit teaching is recognized by _is_explicit_teaching(). Question-shaped text that merely contains words such as “learn” or “teach” is not treated as a teaching command. This prevents accidental learning from ordinary questions.

10. Voice input and voice reply

flowchart LR A[Microphone button] --> B[Browser speech recognition] B --> C[Transcript in chat textbox] C --> D[User presses Send] D --> E[process_input] E --> F[Text answer] F --> G{Voice reply enabled?} G -- Yes --> H[Piper offline TTS] H -- Failure --> I[edge-tts fallback] I --> J[Audio player outputs] G -- No --> K[Text-only response]

The current UX intentionally places the live transcript into the normal message textbox. Stopping recognition leaves the text available for review; pressing Send sends the exact text through the same chat path as typed input. Voice reply generation is separate from recognition and is controlled by the “Enable Voice Reply” checkbox.

The Learning tab is agent-scoped when an agent is selected. Switching agents changes the feedback, memory-event list, and task library to that agent. The shared/default workspace uses the shared memory tables.

12. Output contract between handlers and Gradio

Chat events use one shared output tuple so send, Enter, document upload, and voice-related actions update the same surfaces. The tuple contains:

  1. Chat history and state
  2. Conversation message table and message state
  3. Execution activity
  4. Learning activity
  5. Episodic memory table
  6. Task plan and learning telemetry
  7. Memory overview and task library
  8. Agent knowledge overview
  9. Voice reply players
  10. Composer/document/sidebar updates

Keeping this positional contract aligned is critical. If an output is inserted or reordered, every event declaration in app.py must be updated at the same time.

13. Security, privacy, and knowledge boundaries

  • Custom agent documents and procedures are keyed by agent_id.
  • The custom prompt cannot override the strict zero-prior knowledge rules.
  • Document excerpts are bounded before being sent to the LLM.
  • Unknown questions should produce a refusal instead of a fabricated answer.
  • Medical, legal, finance, and home-maintenance agents include domain-specific safety boundaries in their prompts and documents.
  • File display uses the basename rather than exposing the temporary upload directory.

14. How to explain the system in five minutes

  1. Start with isolation: every custom agent has its own identity, instructions, tasks, documents, and feedback.
  2. Show creation: name, domain, and prompt are stored in the agent record; selecting an agent reloads those fields for editing.
  3. Show learning: a task is procedural knowledge; a document is searchable reference knowledge.
  4. Show answering: the knowledge gate checks the selected agent before the LLM is allowed to answer.
  5. Show evidence: the Learning tab reports recall, unknown, and learnt values, scoped to the active agent.
  6. Show multimodality: speech and camera are input adapters; they eventually use the same process_input() pipeline.
